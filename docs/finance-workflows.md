# Finance workflows

Start by checking the company with `get_company_info`. The desktop connection advertises its full set during MCP initialisation and via `tools/list`. Open the selected tool's input schema for its parameters. Scope each review by company, account, date and currency.

| Request | Evidence and tools | Deliverable |
| --- | --- | --- |
| Review a weekly receipts folder | Inventory originals in Drive. Compare merchant, date, amount, currency, location and card with posted `Purchase` lines and existing `Attachable` files via `query`. Use dated correspondence and calendar events to corroborate purpose. | Record payer, beneficiary, client or event, candidate transaction, supporting evidence and unresolved alternatives. Two same-value purchases need further evidence. |
| Learn historical classifications | Use `list_accounts`, `query_account_transactions`, `get_expense` and `get_bill` to inspect actual expense lines, splits and funding accounts. | Examples and exceptions by merchant and purpose. A personal card identifies the payer. The event or engagement establishes who benefited. |
| Identify gaps in bank evidence | Page through posted transactions and `Attachable` records. Join every file reference on both entity type and ID. Check related bills, invoices and settlements. Count note-only records separately. | Separate a direct file, related evidence, an unlinked upload and a file still to locate. Report the pending bank-feed queue as unobserved unless a dated export or banking view was reviewed. |
| Attach a new file | Resolve the posted transaction. Use `create_receipt_attachment` to preview the filename, target and digest. | If authorised, apply the reviewed bytes to the same target. Keep the returned attachment ID. After an uncertain response, check the attachment list before retrying. |
| Reuse an uploaded file | Query `Attachable`, read its filename and existing references, then preview `link_receipt_attachment`. Use `Purchase` for a posted expense. | If authorised, apply the reviewed revision. Repeated links are harmless. A concurrent change calls for a fresh preview. QBO receipt capture inbox items must first be available as API file attachments. |
| Recover a personally paid client cost | Identify payer, business beneficiary, end client, evidence, currency and any existing reimbursement or recharge. Check customer invoices, bills and the accountant's agreed treatment. | Show reimbursement and onward billing separately. Preview `create_invoice` only for an authorised recharge amount, customer and service item. Preserve the original payer and avoid recording a second bank expense. |
| Prepare billing or chase payment | Find `Invoice` by `DocNumber`, read `get_invoice`, use `get_invoice_pdf` for the original, and `get_report` with `aged_receivables` for debtors. | A dated open-invoice list or the requested PDF. Use `receive_payment` only for an evidenced settlement. |
| Review suppliers and cash movement | Use `aged_payables`, `get_bill`, `get_bill_payment` and vendor credits. Compare internal funding movements using the two account registers. | Identify outstanding bills, credits and settlements. Use `create_transfer` for movement between company accounts when requested. |
| Report revenue, profit and cash | Use `get_profit_loss` with dates and cash or accrual basis, `get_balance_sheet` at period end, and `get_report` with `cash_flow`. Use sales-by-customer for revenue concentration. | State period, currency and basis. Reconcile reported income and costs to net profit. Report debtor and creditor ageing separately. |
| Assemble an accountant handover | Combine `get_trial_balance` with flags, `account_period_summary`, source reports and selected supporting records. Check outstanding questions in correspondence. | A dated evidence index, outstanding items and their owners. A learning review leaves posting, attachments, classifications and distribution to a separately requested action. |

## Fictional evaluation

To reproduce the Windows PR check, run `npm ci --ignore-scripts`, `npm audit`, `npm run build`, `npm run test:desktop`, `node scripts/smoke-mcp.mjs` and `npm run eval:discovery`. The workflow suite passes MCP calls through the normal dispatcher into an in-memory company. Its client has no credentials, and its HTTP stub rejects any unrecognised route. Test uploads use invented bytes. The startup and search checks only initialise the server and list tools.

The discovery metric is the number of labelled requests whose expected tool appears in the first three title/description matches. Each line records the request, accepted tools, candidates and outcome. Pass an alternative built `dist/index.js` to the discovery script to compare revisions. These are development cases with a deterministic lexical ranker. A model choosing among the candidates, external email/calendar matching and an end-to-end Intuit sandbox exercise require separate evidence.

The workflow cases check receipt coverage with colliding IDs, preview-only behaviour, duplicate links, revision conflicts, response verification, customer recharges and period reporting. Expected outcomes come from the invented scenario, including two £24 fares, £800 income and £250 costs. The rest of the repository suite covers payments, transfers, suppliers, ledger reports, authentication and schema validation. The desktop smoke check compares every wire schema, description and permission annotation with its definition and every published name with the README.

Intuit documents the multipart file upload, the metadata update for an existing file and the transaction reference query. [Intuit attachment workflow](https://static.developer.intuit.com/output_html/qbo/docs/workflows/attach-images-and-notes.html)

The installed baseline surfaced the expected tool for 11 of 14 requests. The first candidate reached 13. An unpaid-supplier-bill search still surfaced bill creation, payment and deletion. Adding supplier and ageing terminology to the report description brought the development result to 14 of 14. The receipt audit and existing-upload cases account for the other two changes.
